# Baked Narration — Design

*2026-07-22*

Replace the browser's `speechSynthesis` narration with audio files pre-generated by
OpenAI's text-to-speech API, one file per koan section, committed to the repo and
lazy-loaded per case.

## Why

`speechSynthesis` was chosen because it costs nothing and ships nothing. In practice
its voices vary wildly by browser and platform: Chrome's are acceptable, Firefox's are
not, and neither is *calm*. The reading is a first-class part of this piece — the whole
app is a room built around someone reading these forty-eight stories aloud — and a
robotic reader undercuts every other decision in the art direction.

Generated audio fixes the quality floor and makes the reading identical for every
reader. It costs one round of API spend and roughly 15–40 MB of committed assets.

**This reverses design-doc revision note 7 (2026-07-17)**, which recorded that Frank
passed on pre-generated audio and shelved §9's baked-audio note. A new dated revision
note supersedes it as part of this work.

## Size of the job

From `src/koans/text/mumonkan.js`, 49 entries × (case + comment + verse):

| | |
|---|---|
| Total characters | 42,616 |
| Approximate words | 7,750 |
| Audio at ~120 wpm | ~65 minutes |
| Longest single unit | 2,329 chars (case 2, the story) |
| Shortest units | ~50 chars (verses) |
| Files produced | 147 |
| Cost per full bake | ~$1–2 on `gpt-4o-mini-tts` |

A full re-bake is cheap enough to run several times while tuning. That fact drives
several decisions below — notably dropping the `speechSynthesis` fallback, since there
is never a long window of half-narrated cases.

## Decisions

1. **One narrator throughout.** A single voice reads case, comment, and verse.
   Pace and tone shift per section through prompt instructions, not through casting.
   Consistent with the single-ink aesthetic; multi-voice reads as audiobook production.
   **Chosen by audition: `onyx` on the `japanese` delivery preset** — see below.
2. **Audio is committed to the repo.** Served as static files, lazy-loaded per case.
   Offline and PWA work with no extra infrastructure and no build step — matching the
   project's existing no-build posture.
3. **No `speechSynthesis` fallback.** The old engine and its voice-picking heuristics
   are deleted. A missing file resolves exactly like a finished one, so the UI never
   hangs; it is simply silent.
4. **Per-section granularity.** 3 files per case, matching the existing
   `onSpeak(key)` / `speakAll` interface. No change to how reading works on screen.

## Components

### `scripts/build-narration.js` — the bake

Reads `src/koans/text/mumonkan.js`, the same generated text the app renders, so audio
can never drift from what is on screen.

- **Request:** `POST /v1/audio/speech` with `model: "gpt-4o-mini-tts"`,
  `response_format: "mp3"`, and `voice` / `instructions` from a config block at the top
  of the file. Plain `fetch` — Node 20 has it globally, and the repo has zero
  dependencies, which this work preserves.
- **Output:** `audio/narration/k01-case.mp3`, `k01-comment.mp3`, `k01-verse.mp3`, …
- **Manifest:** `audio/narration/manifest.json` records, per unit,
  `sha1(text + voice + model + instructionsVersion)` plus byte size and duration.
  Re-running regenerates only units whose hash changed. Editing one case's text and
  re-running rebakes one file.
- **Flags:** `--case N`, `--section case|comment|verse`, `--voice NAME`, `--force`,
  `--dry-run` (character counts and a cost estimate, no API calls).
- **Key:** `OPENAI_API_KEY` from the environment, falling back to
  `local/openai-key.txt`. `local/` is gitignored; the key never enters the repo.
- **Robustness:** 4 concurrent requests; exponential backoff on 429 and 5xx; a hard
  assert that no unit exceeds 4,000 characters. The documented input limit is 4,096 and
  our longest unit is 2,329, so the assert never trips today — it exists to fail loudly
  rather than silently truncate if the source text ever changes.

### Instructions — the humanization lever

`gpt-4o-mini-tts` is the only model accepting an `instructions` parameter, which
controls pace, tone, intonation, and delivery in plain English. This is where a calm,
human reading is won or lost, and it is the cheapest thing in the system to iterate on.

Base instruction:

> Voice: an older teacher reading aloud to a small room, to people who already know the
> material. Unhurried, warm, plain.
> Pace: slow, roughly 110 words per minute. Come to a full stop at every period. Take a
> longer breath at paragraph breaks.
> Tone: level and dry. Where the text is wry or sarcastic, let it be dry, not arch.
> Never theatrical, never hushed-and-reverent, never "sage-like."
> Dialogue: read quoted speech plainly, with only the faintest shift between speakers.
> No character voices.
> Read only the text given. Add no words, titles, or commentary.

Per-section overrides: the verse is slower and honors line breaks; Mumon's comment is
slightly more conversational, since he is talking back to the story.

Paragraph breaks in the source are preserved in the request body — the model reads them
as pause cues, so no silence needs to be stitched between clips.

### `scripts/narration-audition.js` — the bake-off

Generates a matrix of candidate voices × instruction presets over two fixed passages:
case 7 (short, with dialogue) and case 33's verse (four lines). OpenAI's documentation
calls out `marin` and `cedar` as highest quality; `sage`, `ballad`, `ash`, and `fable`
are plausible for this register.

Output goes to `local/audition/` (gitignored) with a generated `audition.html` — a plain
list of labeled play buttons for back-to-back comparison. Costs pennies. The winner is
recorded in the bake script's config.

**Result.** Round one auditioned marin, cedar, sage, ballad, ash and fable on the
`plain` preset; ash won, cedar and fable were out. Round two added the deeper
male-sounding `echo` and `onyx`, and introduced accent presets — accent is instructed,
not a property of the voice, and the model supports it directly. **`onyx` on `japanese`
was chosen.** Total audition spend: about 18 cents.

Two measurements came out of the audition that shape the rest of the work:

- **The accent instruction also slows the read.** Onyx's dialogue sample ran 208 KB on
  `plain` and 290 KB on `japanese` — same text, ~40% longer. The accent presets deliver
  the "slow and thoughtful" instruction harder than `plain` does. If the pacing is
  wanted without the accent, that language is separable.
- **Takes drift.** `ash-plain-verse` came out 254 KB in round one and 305 KB in round
  two — identical voice, preset and text, 20% apart. Across 147 independently generated
  files, pacing will vary somewhat case to case regardless of settings. Mitigation is
  per-file re-rolls, which the manifest makes cheap; there is no way to make separate
  generations deterministic.

### Runtime — `src/audio/narration.js`

Split along the project's testable-state line:

- **`src/audio/narration_state.js`** (pure, unit-tested): `narrationPath(id, section)`,
  manifest lookup, queue ordering. No DOM, no WebGL, runs under `node --test`.
- **`src/audio/narration.js`** (browser-only): a single reused `HTMLAudioElement`.
  Retains the generation-counter pattern from the current implementation, which
  neutralizes stale async callbacks after `stop()`.

The public interface changes from `speak(text, opts)` to `speak(id, section, opts)`.
Three call sites in `src/main.js`. Highlight-follows-audio, stop-on-exit, and
stop-on-sit are unchanged.

**Deleted:** `chunkSentences`, `chooseVoice`, the GOOD/BAD voice-name heuristics, and
the `gate.voices()` / `setVoice()` / `sampleVoice()` tuning surface in `main.js`, along
with the `gateless-gate-voice` localStorage pin. Voice is decided once, at bake time.
`gate.voice()` survives, reporting what shipped (`"onyx / japanese"`).

**Added while in here:** `audio.duck(on)` in the engine, pulling the master gain from
0.8 to 0.32 while narration reads. Narration plays through an `<audio>` element outside
the Web Audio graph, so ducking the master touches only the ambience bed — which is the
intent. Gating narration volume behind the sound toggle was considered and deferred:
pressing "read" with sound off and getting silence is worse than the current behaviour,
and the right answer needs a UI decision rather than an audio one.

## Assets

`audio/narration/*.mp3`, committed, fetched per case on demand. Never bundled, so the
~1.5 MB app budget is unaffected — the budget covers code and the initial load, and
narration is neither.

**Measured:** case 1's three files came to 2.1 MB for 2,125 characters — almost exactly
1 KB per character, putting the full book at **~42 MB** of mp3.

That is large enough to matter, and it is why `audio/narration/` is gitignored for now:
committing a 42 MB bake on every tuning pass would leave all of it in git history
permanently. The directory is un-ignored once voice and instructions are final, so
exactly one bake lands in history.

If 42 MB proves too heavy to ship, the escape hatch is `response_format: "opus"`
(roughly a third the size) — already supported via `--format`. The cost is older Safari,
which would need an mp3 source-set fallback, and baking both formats puts the total back
near 55 MB. Decide with real numbers, not in advance.

**PWA note for M2:** the service worker must not precache narration. Baking tens of
megabytes into the install step would be hostile on mobile data. Cache-on-play only.

## Testing

- `tests/narration-state.test.js` — path construction, manifest lookup, queue order for
  cases with an empty section, behavior when a manifest entry is missing.
- `scripts/build-narration.js --dry-run` — asserts every unit is under the length limit
  and reports totals. Runs without network or a key.
- No test touches the network. Audio quality is judged by ear, not by assertion.
